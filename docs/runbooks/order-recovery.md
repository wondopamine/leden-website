# Order Recovery Runbook

Status: owner approval required before launch rehearsal

The database commit is the acceptance boundary. Email, audio, a browser response, and Realtime delivery are not authoritative. Use the authorized staff board and canonical refresh; never query public order data with a display order number alone.

## First response

1. If acceptance or board truth is uncertain, pause new online ordering with the confirmation-protected control.
2. Keep already accepted orders visible and operational; pausing never cancels them.
3. Record the time, staff operator, visible safe error code, board freshness state, and affected display order numbers. Do not copy customer PII or private links into a ticket or chat.
4. Use manual Refresh. If canonical refresh succeeds, work from its status/version. If it does not, keep transitions disabled and switch to the owner-approved counter/phone fallback.
5. Escalate database or platform outages to the named technical owner. Do not use direct SQL to repair status.

## Customer lost or interrupted checkout

- A dropped create response is expected to enter receipt recovery. The customer must not resubmit while the outcome is still uncertain.
- An identical committed attempt returns the same receipt. Changed material under the same attempt conflicts and must not create a second order.
- If recovery proves the attempt absent, the same active attempt may retry with a fresh challenge. If recovery remains uncertain, keep it non-resubmittable and use manual support.
- If the private tracking link was lost, expired, removed, or revoked, it cannot be reconstructed: the database stores only its digest. Authenticated staff may confirm the current order state by approved internal search and speak to the customer, but must not create a replacement bearer link or expose internal IDs.
- Public confirmation links and display order numbers never authorize a lookup.

## Realtime or board degradation

| Board state | Meaning | Staff action |
| --- | --- | --- |
| Live | Realtime connected and canonical refresh is fresh | Normal compare-and-set transitions |
| Reconnecting | Last-known queue retained, connection degraded | Watch freshness; do not claim event hints are truth |
| Polling | Realtime unavailable, canonical polling is succeeding | Continue while fresh; use visible manual Refresh as needed |
| Stale | No successful canonical refresh for 45 seconds | Stop transitions, pause ordering if needed, use fallback |

Realtime messages are refresh hints only. Never update or delete an order based solely on an event payload. Focus/network recovery and mutation completion must reconcile through the authorized no-store boundary.

## Accidental terminal action

`picked_up` and `cancelled` are terminal. There is no hidden reversal, recall state, or direct-update exception.

1. Do not edit the database or insert a compensating event.
2. Tell the shift lead immediately and record the order number, canonical status/version, time, and operator—without copying customer PII outside approved systems.
3. Use the staff-only phone shown in the cancellation workflow to contact the customer when appropriate.
4. Fulfil or refund operationally according to the café owner's manual process; this product has pay-at-pickup and no online payment reversal.
5. If the error suggests a wider staff/process issue, pause ordering and rehearse the confirmation flow before resuming.
6. Preserve the immutable event history for review.

## Suspected duplicate or conflict

- Search the authorized board for the display order number and compare canonical status/version.
- One idempotency attempt must map to one order and one initial event. Do not merge or delete orders manually.
- A transition conflict means another canonical action won. Refresh, explain the current safe state, and perform only an allowed next action if still needed.
- If two genuine orders exist for different attempts, treat both as accepted until the shift lead resolves the customer interaction; do not silently remove one.

## Tracking-secret or privileged-key exposure

For a private customer link:

1. Treat anyone with the link as able to view its PII-free status.
2. Ask the technical owner to revoke tracking for that order through a reviewed, authorized operation.
3. Confirm the public status endpoint returns the same unavailable response as an invalid secret.
4. Staff continue through the authenticated board; no replacement link is generated by this phase.

For a privileged application key:

1. Pause ordering if server integrity is uncertain.
2. Rotate to a new target-specific key, update server-side secret storage, and restart or deploy every consumer.
3. Revoke the old key immediately after the new path is healthy.
4. Prove the old key is denied and review Auth/database audit evidence.
5. Never retain a legacy fallback just in case.

## Database outage or restore

Follow `docs/runbooks/supabase-backup-restore.md`. A restore is destructive, owner-approved, and performed while ordering is paused and manual fallback is active. After restore, validate migrations, allowlist authorization, atomic create/replay/recovery, compare-and-set transitions, event ordering, Realtime/polling, tracking expiry/revocation, and exact cleanup before reopening.

## Reopening checklist

- Canonical Refresh succeeds and board state is fresh.
- Accepted active orders are reconciled and assigned to staff.
- No ambiguous customer attempt is being invited to resubmit.
- Pause/resume works and storefront availability follows it.
- A synthetic order can be created, transitioned, tracked, and cleaned exactly.
- Shift lead and technical owner record approval.
